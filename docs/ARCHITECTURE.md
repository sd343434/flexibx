# Flexibx architecture

Status: **Phase 1 — foundation** (completed), **Phase 2 — authentication and runtime
multi-tenancy** (completed) and **Phase 3 — Marketing Core OS** (completed,
see §10 and [`PHASE_3_MARKETING_CORE_OS.md`](PHASE_3_MARKETING_CORE_OS.md)). This
document describes what exists, the rules every later phase must follow, and what is
intentionally deferred.

Phase 2 was executed step by step according to [`PHASE_2_PLAN.md`](PHASE_2_PLAN.md), the
canonical Phase 2 plan (its §1 maps the executed steps to the planned ones).

## 1. Shape of the system

A single Next.js 16 application (no monorepo). Clear layering inside `src/`:

```
src/
├─ proxy.ts             Edge of page requests: locale, CSP nonce, session-cookie renewal, last-workspace cookie. No authz.
├─ app/                 Routes only (pages, layouts, route handlers). Thin.
│  ├─ [locale]/         Root layout (<html lang dir>), pages, error / not-found
│  └─ api/              health/ (liveness/readiness), auth/[...all] (Better Auth's public endpoints)
├─ components/          Client-safe UI (ui/ primitives, common/ app components)
├─ lib/                 Client-safe helpers
├─ i18n/                Locale config, routing, request config, navigation
├─ security/            CSP builder
├─ server/              Server-only domain + infrastructure
│  ├─ env*.ts           Zod-validated configuration (lazy)
│  ├─ logger.ts         pino + secret redaction (redact.ts)
│  ├─ errors/           AppError, error-code registry, HTTP mapping
│  ├─ validation/       Zod → localized field-error codes, parseInput
│  ├─ http/             withRoute(): validation, errors, request id, latency logs
│  ├─ db/               Prisma 7 client factory, tenant guard, singletons
│  ├─ tenancy/          Roles, permission matrix, TenantContext
│  ├─ audit/            Append-only audit log
│  ├─ workspaces/       Workspace service (soft delete), member repository
│  ├─ storage/          StorageService interface, S3 / Wasabi / memory adapters, provider router
│  └─ health/           Dependency health checks
└─ generated/prisma/    Generated Prisma client (gitignored)
```

**Layering rules (enforced by ESLint `no-restricted-imports`):**

- `src/app/**` must not import Prisma, the generated client or `@/server/db/*` — routes
  call services in `src/server`.
- `src/components/**` and `src/lib/**` must not import anything from `@/server`.
- Server modules that hold secrets or connections import `server-only`.
- Services receive their database client as a parameter (`Db`), which keeps them testable
  and lets callers pass a transaction.

A background worker (BullMQ) will later be a second entrypoint (`src/worker/`) in the same
package, reusing `src/server` — no restructuring required.

## 2. Request flow

```
Browser ──► proxy.ts ──► [locale] layout/page (server components) ──► server services ──► Prisma (guarded) ──► PostgreSQL
              │ locale redirect (/ → /ar|/en)
              │ per-request CSP nonce
API client ─────────────► app/api/*/route.ts = withRoute({ query, body, params, handler })
                            ├─ request id (x-request-id), body size cap, Zod validation
                            ├─ handler → services (TenantContext + permission checks; Phase 2 adds auth)
                            └─ errors → { error: { code, messageKey, requestId, fields? } }
```

## 3. Error model

- One error type, `AppError(code, { message, metadata, fields, cause })`.
- `code` comes from the registry in `server/errors/codes.ts`, which defines the HTTP status.
- `userMessageKey` = `errors.<code>`: the friendly Arabic/English text lives in
  `messages/{ar,en}.json`. Validation failures carry `fields: [{ path, code, params }]`,
  translated via `validation.<code>` (ICU messages, e.g. `{minimum}`).
- Responses never contain prose, stack traces, SQL or metadata. Unknown errors become
  `INTERNAL`; the `requestId` correlates the response with server logs.
- 5xx are logged with the (redacted) error and stack; 4xx are logged as warnings without
  stacks.

## 4. Database foundation

PostgreSQL 16 via Prisma 7 (`prisma-client` generator, `@prisma/adapter-pg` driver adapter,
`prisma.config.ts` for schema/migrations/seed).

Conventions:

- UUID primary keys generated by PostgreSQL (`gen_random_uuid()`; no pgcrypto).
- `snake_case` tables/columns via `@@map`/`@map`; `timestamptz(3)` timestamps.
- Every workspace-owned table has `workspace_id uuid NOT NULL REFERENCES workspaces ON DELETE CASCADE`,
  indexes leading with `workspace_id`, and is registered in `TENANT_MODELS`.
- Extensions and `CHECK` constraints live in migration SQL.

Phase 1 tables:

| Table               | Notes                                                                                                                                                                                                             |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users`             | `email citext UNIQUE`; shape compatible with Better Auth's core user (Phase 2)                                                                                                                                    |
| `workspaces`        | Tenant root. `slug citext UNIQUE` + `CHECK (slug::text ~ '^[a-z0-9-]{3,48}$')`; `type` BUSINESS/AGENCY; `parent_workspace_id` (agency → client, `ON DELETE RESTRICT`, `CHECK` not self); `deleted_at` soft delete |
| `workspace_members` | Tenant-owned. `UNIQUE (workspace_id, user_id)`; role OWNER/ADMIN/MANAGER/EDITOR/VIEWER/CLIENT                                                                                                                     |
| `audit_logs`        | Append-only. `workspace_id` nullable (platform events), **`ON DELETE RESTRICT`**; actor `ON DELETE SET NULL`                                                                                                      |

**Deletion policy.** Workspaces are soft-deleted (`deleted_at`) by
`softDeleteWorkspace()`, which also writes an audit entry in the same transaction. The
tenant guard blocks hard deletes of workspaces through the application client, and the
database refuses to delete a workspace that still has audit history. A future, controlled
**purge job** (retention policy / data-erasure requests) may permanently delete a
workspace's data using the system client; it is intentionally not implemented yet.

## 5. Multi-tenant isolation

Model: shared database, shared schema, scoped by `workspace_id`. Users belong to many
workspaces through `workspace_members`.

Controls, from outermost to innermost:

1. **Server-side authorization only.** The proxy does no authorization.
   - `getCurrentUser()` / `requireUser()` (`server/auth/session.ts`) read the user from the
     signed session cookie through Better Auth's `getSession` (expiry and revocation
     included).
   - **Rolling sessions.** Server Components cannot write cookies, so the session cookie
     is renewed where it can be: the proxy asks Better Auth's own `get-session` endpoint
     (in-process) on every page request that carries a session cookie and forwards only
     the renewed or cleared session cookie (`server/auth/session-refresh.ts`; at most one
     renewal per day). Better Auth's `nextCookies()` plugin writes cookies for server
     actions and route handlers and skips the refresh inside a Server Component render,
     so the database expiry never runs ahead of the browser cookie. The proxy still makes
     no authorization decision; a refresh failure is logged and never blocks a page. They return a small frozen `AuthUser` with no session data.
     No session → `UNAUTHENTICATED` (401).
   - `requireWorkspaceAccess(slug, action?)` (`server/tenancy/access.ts`) runs session →
     membership lookup by URL slug → optional `assertCan`, and is the only producer of a
     `TenantContext { userId, workspaceId, role }` for existing workspaces (a static test
     keeps `createTenantContext` inside `server/tenancy/`). Workspace id and role come only
     from the membership row; client-supplied ids, roles and headers are ignored. A
     malformed, unknown, soft-deleted or foreign workspace all yield the same
     `NOT_FOUND` (404); a member lacking the permission gets `FORBIDDEN` (403).
   - API routes (`withRoute`) and server actions (`withAction`) call these primitives in
     their handlers. `withRoute` also rejects cookie-bearing mutations that are not
     same-origin with `APP_URL` (CSRF); Next.js performs the equivalent check for server
     actions. `safeNextPath()` accepts only internal `/{locale}/…` paths for post-sign-in
     redirects.
   - **Workspace creation** (`createWorkspace`, `server/tenancy/workspace-creation.ts`):
     any signed-in user (email verification not required in Phase 2) creates a workspace
     from `{ name, slug, defaultLocale }` only. The strict input schema
     (`server/workspaces/workspace-input.ts`) rejects every other key. The server fixes
     the rest: type `BUSINESS` (AGENCY/client workspaces are Phase 14), the session user
     as creator, role `OWNER`. One transaction on the guarded client inserts the
     workspace, the OWNER membership and the `workspace.created` audit entry (metadata:
     `slug`, `type`, `defaultLocale`, `ownerRole`), so all three exist or none do. The
     audit entry's `TenantContext` is built from the membership row the same transaction
     inserted. Slugs are trimmed and lowercased, then checked with the database `CHECK`
     rule (`server/tenancy/slug.ts`). A slug already in use, including by a soft-deleted
     workspace, is reported as `CONFLICT` with a `slug` field error `slug_taken`. The
     server action `createWorkspaceAction` (`withAction` + `requireUser()`) backs the
     form at `/{locale}/workspaces/new`. The form reads only those three fields and
     then redirects (next-intl `redirect`) to `/{locale}/w/{slug}`.
   - **Workspace selection**: `/{locale}/workspaces` lists the user's own memberships in
     non-deleted workspaces (`listMyWorkspaces`, a reviewed system-client path filtered to
     the session user). Zero workspaces → `/workspaces/new`; otherwise the last workspace
     (see below) when it is still one of the user's memberships; exactly one → into it;
     several → the list. `?list=1` always shows the list. Without a session these pages
     redirect to the sign-in page with a `next` return path (`requirePageUser`). All of
     them are dynamic and served with `Cache-Control: private, no-cache, no-store`.
   - **Workspace app shell** (`app/[locale]/w/[workspaceSlug]/layout.tsx` + `page.tsx`):
     the layout and every page call `loadWorkspace(locale, slug)` (React `cache`, so it
     runs once per request). Layouts are not re-run on client navigation, so a page never
     relies on its layout's check. `loadWorkspace` = `requirePageUser` →
     `getWorkspaceShell` (`requireWorkspaceAccess(slug, "workspace.view")`, the row via
     the guarded client, `listMyWorkspaces` for the switcher). Foreign, unknown,
     soft-deleted and malformed slugs all render the same localized 404. The shell
     (`components/shell/*`) is presentational: workspace name, a workspace switcher (the
     user's own memberships; switching is plain navigation to `/{locale}/w/{slug}`, which
     authorizes again), a user menu (name, email, role in this workspace, sign-out) and
     workspace navigation that lists only pages that exist and the role may open (Home;
     Members for roles with `member.view`). No workspace identity or role lives in
     client state.
   - **Last workspace** (decision 10, `server/workspaces/last-workspace.ts`): for
     browsers with a session cookie, the proxy remembers the slug of the last visited
     `/{locale}/w/{slug}` page in `flexibx.last_workspace` (HttpOnly, SameSite=Lax,
     Secure on https, 90 days). It is a convenience only: `/workspaces` uses it just when
     it names one of the user's current memberships (`getMyWorkspaceLanding`). A foreign,
     deleted, unknown or malformed value is ignored, and it never grants access.
   - **Members** (`/{locale}/w/{slug}/members`, `server/workspaces/member-service.ts`):
     every role with `member.view` sees the member list (CLIENT does not); OWNER and
     ADMIN (`member.updateRole` / `member.remove`) change roles and remove members. The
     existing `canAssignRole` ceiling applies to both the member's current role and the
     new one, so an ADMIN cannot touch an OWNER. Grantable roles are ADMIN, MANAGER,
     EDITOR and VIEWER (`GRANTABLE_ROLES`): nobody can be made OWNER (no ownership
     transfer) and CLIENT is not offered in BUSINESS workspaces. Nobody changes their own
     role or removes themselves (they leave instead). Any member may leave, except the
     last OWNER. Each mutation runs in one transaction that first locks the workspace row
     (`lockWorkspaceMemberships`, `SELECT … FOR UPDATE`) and re-reads the actor's
     current role, so a demotion since the request started is respected and two
     concurrent changes can never leave a workspace without an OWNER. Member ids from
     other workspaces are `NOT_FOUND`. Audit: `member.role_changed`, `member.removed`,
     `member.left`.
   - **Invitations** (`workspace_invitations`, tenant-owned, registered in the tenant
     guard): OWNER/ADMIN invite an email with a grantable role. The token is 32 random
     bytes (base64url) shown once to the inviter as a link built from `APP_URL`
     (`/{locale}/invite/{token}`); only its SHA-256 hex is stored. Creation is limited per
     inviting user and acceptance per client (see rate limiting below). Invitations expire
     after 7 days. The database adds: one pending invitation per (workspace, email)
     (partial unique index), `role <> 'OWNER'`, a hex-only hash and "accepted or
     revoked, never both". An expired pending invitation is replaced by a new one;
     inviting a member or an address with a live invitation is a `CONFLICT` on `email`.
     Inviters see the pending list and can revoke (link stops working at once). Audit:
     `member.invited`, `invitation.revoked` (email and role, never the token or its
     hash).
   - **Accepting** (`server/tenancy/invitation-acceptance.ts`, a reviewed system path):
     the invitee has no `TenantContext` yet, so the token hash is looked up with the
     system client. Everything after that runs in one guarded transaction scoped to the
     invitation's workspace: lock, conditional claim (`UPDATE … WHERE accepted_at IS
NULL AND revoked_at IS NULL AND expires_at > now`; zero rows → invalid), membership
     insert, `invitation.accepted` + `member.added` audit. Unknown, malformed, expired,
     revoked, used and deleted-workspace tokens are all the same `NOT_FOUND`
     (`invitation_invalid`). The signed-in email must equal the invited one (case
     insensitive); other accounts get `invitation_email_mismatch` and see no workspace
     details. An existing member gets `CONFLICT` and the invitation stays open. The page
     requires a session first: anonymous visitors go to sign-in with `next` set to the
     invitation (sign-up keeps it), in the same locale. It is `noindex` and
     `no-referrer`. The application logger redacts the token after `/invite/` (also
     URL-encoded, as in `?next=%2Far%2Finvite%2F…`) in any logged string, and
     `next.config.ts` keeps every URL matching `INVITATION_URL_PATTERN` out of the
     `next dev` request log (`next start` logs no request URLs).
   - **Mailer** (`server/mail/`): `Mailer.send({ to, locale, template, data })` with
     localized templates (`messages/*.json` → `emails`) whose interpolated values are
     HTML-escaped. Transports: `MemoryMailer` (tests), `LogMailer` (development: logs
     template, locale and a masked recipient — never the subject, body or link) and
     `UnconfiguredMailer` (production: every send throws `SERVICE_UNAVAILABLE`,
     `mailer_not_configured`). No real provider exists yet, so no environment reports an
     email as sent: the invitation is committed first and the inviter is told "no email
     was sent" and shown the link to share manually.
   - **Authentication pages** (`/{locale}/sign-up`, `/{locale}/sign-in`, route group
     `app/[locale]/(auth)`): their form actions call `signUpAction` / `signInAction` /
     `signOutAction` (`server/auth/auth-actions.ts`, `withAction`), which use
     `signUpWithEmail` / `signInWithEmail` / `signOutCurrentSession`. Better Auth's
     `nextCookies()` writes and clears the session cookie; application code never handles
     tokens. Sign-up answers every accepted request — new or already-registered email —
     with the same redirect to sign-in (`?registered=1`, no automatic sign-in). Only
     invalid input is reported, per field, and the password is never echoed. Every
     sign-in failure shows the single `auth.errors.invalidCredentials` message;
     outcomes map to `auth.errors.*` keys (`server/auth/auth-messages.ts`), never to
     library text. After sign-in the user goes to `postSignInPath(next)`, which is
     `safeNextPath` or `/{locale}/workspaces`. Signed-in users visiting the auth pages are
     sent the same way. Sign-out deletes the current database session and expires its
     cookie (other sessions of the user stay valid), then shows the sign-in page.
     Email/password inputs are `dir="ltr"` in both locales.
   - **Email verification** (Step 8, decision C6): Better Auth's stateless signed tokens
     (HS256 with `AUTH_SECRET`, 1-hour expiry, nothing stored). Sign-up sends the link in
     the sign-up page's locale. **Sign-in and workspace creation never require a verified
     email** (decision C1; human decision in Step 9): an unverified account signs in, in
     production too, and is a normal session user. The policy
     `AUTH_REQUIRE_EMAIL_VERIFICATION` (unset: required in production only, C6) applies
     only to **verified-only operations**, which call `requireVerifiedEmail`
     (`server/auth/verified-email.ts`) before doing anything else. In Phase 2 that is
     accepting a workspace invitation (and its preview), whose only proof of identity is
     the invited address (C4): an unverified account gets `FORBIDDEN`
     `email_not_verified` (the page shows "verify your email first") before the token is
     looked up, so it learns nothing about the invitation.
     `/{locale}/verify-email`: the user confirms with a button (a POST, so mail scanners
     that prefetch links cannot use the token up). `verifyEmailToken` accepts a token only
     while its account is still unverified, so a replayed, used, expired, forged,
     malformed, email-change or unknown-account token is the same `INVALID_TOKEN`. Resend
     (`resendVerificationEmail`) always answers "if an unverified account uses it, we
     sent a link" (Better Auth also pads that path to 500 ms).
   - **Password reset** (`requestPasswordReset` / `resetPasswordWithToken`): the request
     always answers "if an account uses it, we sent a link"; Better Auth emails only real
     accounts. Tokens: 24 random alphanumerics, 1-hour expiry, stored only as SHA-256
     (`verification.storeIdentifier: "hashed"`), consumed atomically (single use). Unknown,
     used, expired and malformed tokens are the same `INVALID_TOKEN`. A reset hashes the
     new password (scrypt), deletes every session of the account
     (`revokeSessionsOnPasswordReset`), and the user signs in again
     (`/sign-in?reset=1`). Signed-in **password change** (`/{locale}/account/security`,
     linked from the user menu) needs the current password and deletes every other
     session (`revokeOtherSessions`); Better Auth replaces the current session and its
     cookie. There is no session list/revoke UI (C7).
   - **Email links** are built from `APP_URL` as `/{locale}/verify-email#token=…` and
     `/{locale}/reset-password#token=…`. The token is in the URL fragment, which browsers
     never send to a server: it stays out of request logs, proxies and Referer headers.
     The page reads it client-side (also on `hashchange`) and removes it from the address
     bar. Both pages are `noindex` and `no-referrer`. The locale travels through Better
     Auth's callback URL (`/{locale}`).
   - **Email callbacks never throw**: Better Auth calls them only for existing accounts,
     so a mail failure that surfaced would reveal the account. Failures are logged as
     `account email not sent (<template>)` — never the address, link or token.
   - **HTTP surface**: every email/password Better Auth endpoint (sign-up, sign-in,
     request-password-reset, reset-password, verify-email, send-verification-email,
     change-password) is in `disabledPaths`; the public route additionally refuses the
     internal limiter checkpoint and the `/reset-password/:token` callback
     (`isInternalOnlyAuthPath`). Only session reads, sign-out and Better Auth's
     session-management endpoints stay public, under the origin check.
   - **Authentication rate limiting** (Step 8, decisions 8 and C8): Better Auth's own
     limiter, on in every environment, with database storage (`rate_limits`). Its
     limiter runs only in its HTTP router, and Flexibx calls Better Auth server-side
     (`auth.api.*`), which bypasses it — verified, and covered by a test. So every
     Flexibx entry point first passes a **limiter checkpoint**: a request through
     `auth.handler` to the no-op plugin endpoint `/flexibx/rate-limit/<bucket>[/<hmac>]`
     (`server/auth/rate-limit.ts`). That request carries only the configured client-IP
     header (IP buckets) or none (account buckets), so the key is Better Auth's
     `<trusted ip>|<path>`; account buckets put an HMAC (AUTH_SECRET) of the normalized
     email or user id in the path, never the raw value. Policy, one module
     (`server/auth/rate-limit-policy.ts`). **Status: APPROVED — HUMAN DECISION**
     (Phase 2); changing a value needs a new human decision:

     | Bucket                         | Key     | Limit           |
     | ------------------------------ | ------- | --------------- |
     | sign-in                        | IP      | 10 / minute     |
     | sign-in (account)              | email   | 10 / 15 minutes |
     | sign-up                        | IP      | 10 / 10 minutes |
     | password-reset request         | IP      | 5 / 15 minutes  |
     | password-reset request (acct.) | email   | 3 / hour        |
     | password-reset submission      | IP      | 10 / 15 minutes |
     | verification resend            | IP      | 5 / 15 minutes  |
     | verification resend (account)  | email   | 3 / hour        |
     | verify-email submission        | IP      | 20 / 15 minutes |
     | password change                | user id | 5 / 15 minutes  |
     | invitation acceptance          | IP      | 20 / 15 minutes |
     | invitation creation            | user id | 50 / hour       |

     `get-session` (called by the proxy on every page to roll the cookie) is exempt;
     Better Auth's defaults cover its other HTTP paths, none of which takes a password,
     sends an email or consumes a token (`/verify-password` is disabled: its
     `scope: "server"` is not enforced by the router, so it would be a current-password
     oracle outside the change-password limit). The public surface, the
     checkpoint-before-Better-Auth order of every entry point and the call-site list
     are pinned by `tests/integration/auth-entry-points.test.ts`. A limit is `RATE_LIMITED` with
     `auth.errors.rateLimited` / `errors.RATE_LIMITED`, the same whether or not an
     account exists; the checkpoint fails closed on any other error.

   - **Client IP** (decision 8): Better Auth's `getIP`, configured only from
     `AUTH_IP_HEADER` / `AUTH_TRUSTED_PROXIES`. Without them no header is read at all —
     not even `X-Forwarded-For` (`ipAddressHeaders: []`) — and IP buckets fall back to
     Better Auth's single shared bucket per path ("no-trusted-ip"; loopback in
     development and test). A multi-hop chain is trusted only with trusted proxies,
     stripped from the right.
   - **Security audit** (platform-level entries, `workspace_id` null):
     `user.email_verified`, `user.password_reset_requested` (only for an existing
     account; never shown to the requester), `user.password_reset`,
     `user.password_changed`. Rate-limit hits are logged (bucket only), not audited.
2. **Permission matrix** (`server/tenancy/permissions.ts`): the only place that maps roles
   to actions. Services call `assertCan(ctx, action)`. `CLIENT` (an agency's customer) has
   a narrow set: view brand/content/campaigns/analytics and approve content.
3. **Workspace-scoped services and repositories** take a `TenantContext` and build queries
   with `scopedWhere(ctx, …)`, which always pins `workspaceId` (callers cannot override it).
   Records from other workspaces are reported as `NOT_FOUND`, never `FORBIDDEN`.
4. **Tenant guard** (`server/db/tenant-guard.ts`), a Prisma client extension on the default
   client (`getDb()`), which rejects with `TENANT_SCOPE_MISSING` (500, a programming
   error):
   - any non-create operation on a tenant model without `where.workspaceId` (a single
     concrete id; `in`/`not`/`OR` are rejected);
   - creates without an explicit `data.workspaceId`;
   - updates that change `workspaceId`;
   - any update/delete on append-only models (`AuditLog`);
   - `Workspace` reads/updates that do not target one `id`, and all `Workspace` hard deletes;
   - nested writes from `Workspace` creates, updates and upserts to its workspace-owned
     relations (`members`, `auditLogs`, `clients`, `invitations`). Prisma runs nested writes without
     passing them through the extension, so these relations are changed only through
     their own guarded top-level model operations;
   - reaching tenant relations through global models (e.g. `User.memberships`).

   It also applies inside interactive transactions.

5. **System client** (`getSystemDb()`): unguarded, for explicitly reviewed paths only
   (resolving and listing the signed-in user's own memberships in `server/tenancy/access.ts`,
   looking up an invitation by token hash in `server/tenancy/invitation-acceptance.ts`,
   health checks, seed, future purge jobs).
6. **Raw SQL**: `$queryRawUnsafe` / `$executeRawUnsafe` are banned by ESLint. Tagged
   `$queryRaw` bypasses the guard, so it must be workspace-scoped by hand and reviewed.
7. **Storage**: object keys are server-generated as `workspaces/{workspaceId}/{category}/{uuid}.{ext}`;
   `assertKeyBelongsToWorkspace()` checks ownership before any access.
8. **Later (Phase 18)**: PostgreSQL row-level security as a second line of defense.

**Agency mode.** An AGENCY workspace owns client workspaces via `parent_workspace_id`.
Agency staff access a client workspace **only through explicit membership rows**, never by
inheritance, so isolation stays simple and auditable.

## 6. Arabic-first i18n and RTL

- **Routing.** next-intl with `localePrefix: "always"`: `/ar/...` (default) and `/en/...`.
  For `/`, the proxy picks the `NEXT_LOCALE` cookie (explicit choice), then
  `Accept-Language`, then Arabic. Unknown paths and locales render a localized 404.
- **Direction from the server.** `[locale]/layout.tsx` is the root layout and renders
  `<html lang={locale} dir={rtl|ltr}>` from `i18n/config.ts`. There is no client-side
  flipping and no flash. The locale reaches `i18n/request.ts` through Next's
  `next/root-params`.
- **Typography.** IBM Plex Sans Arabic + Inter via `next/font` (self-hosted at build),
  ordered per `:lang()`. Arabic gets a taller line height.
- **Logical CSS only.** UI uses `ms-/me-`, `ps-/pe-`, `start-/end-`, `text-start/end`,
  `border-s/e`, `rounded-s/e`. ESLint rejects physical classes (`ml-`, `pr-`, `left-`,
  `text-right`, …) in `.tsx`, including inside template literals. Direction-sensitive
  icons use `DirectionalIcon` (`rtl:-scale-x-100`).
- **Messages.**
  - `messages/ar.json` is the source of truth. `messages/en.json` must have identical
    keys, which a unit test enforces along with ICU validity and coverage of every error
    and validation code.
  - Keys are typed through `next-intl`'s `AppConfig` (`src/global.d.ts`).
- **Adding a language.** Add it to `LOCALES` and `LOCALE_DIRECTIONS` and add
  `messages/<locale>.json`. If it is stored per user or workspace, extend the Prisma
  `Locale` enum too.

## 7. Security model (Phase 1)

| Area         | Control                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

**Assumptions and known limits.**

- Session tokens: Better Auth stores the raw token in `sessions.token`; the cookie
  carries `token.HMAC(token, AUTH_SECRET)`, so a database copy alone cannot be replayed.
  Controls: `AUTH_SECRET` lives only in the environment (never in the database or its
  backups); rotating it invalidates every session cookie; auth tables are unreachable from
  the application client (tenant guard) and from code outside `server/auth/` (static
  test); Better Auth log output is reduced to redacted message text.
- Without `AUTH_IP_HEADER` (direct exposure or an unconfigured proxy), IP-keyed limits
  are one shared bucket per entry point: abuse by one client then throttles everyone at
  that entry point (account-keyed limits are unaffected). Production deployments must
  configure the trusted header. Better Auth logs a warning once per process when it
  cannot resolve an IP (account buckets trigger it by design).
- Account-keyed sign-in limits let an attacker slow one account's sign-in for 15
  minutes (no lockout state; accepted trade-off against distributed guessing).
- Production email: there is no provider yet (C3). Users can sign up, sign in and create
  workspaces in production, but nobody can verify an address — and therefore nobody can
  accept an invitation — until a provider exists; the production default is intentional
  and documented. `MAIL_TRANSPORT=test-outbox` is for
  end-to-end runs of the production build only; it writes single-use links to disk.
- Verification tokens are stateless: one stays cryptographically valid until it expires
  (1 h) but changes nothing once the account is verified. If an account were deleted and
  re-registered within that hour, an old token could verify the new account (account
  deletion is out of scope in Phase 2).
- Response times: sign-up and password-reset requests take at least 500 ms
  (`withMinimumDuration`, `server/auth/timing.ts`), and Better Auth pads verification
  resends the same way, so the known/unknown-account branches cannot be told apart by
  timing — including once a real email provider makes the "account exists" branch slower.
  Sign-in keeps Better Auth's own equalization (a dummy hash for unknown accounts).
- The credentials in `.env.example`, `docker-compose.yml` and CI are local or throwaway
  defaults.
- Styles allow `'unsafe-inline'`, because Next.js and next/font inject style tags. Scripts
  never do.
- API and AI rate limiting are Phase 6; Phase 2 limits authentication entry points and
  invitations only.
- With verification not required (development, or an explicit `false`), someone who
  registers an invited address without owning it AND obtains the link could accept;
  with the production default this is closed (invitation acceptance is verified-only).
- An unverified account can be registered for an address its creator does not own and
  used to sign in and create workspaces (C1). It cannot accept invitations under the
  production policy, and the real owner can take the account over with a password reset
  (the link goes to the real inbox and ends every session).

  latest change request on the content page until the next decision; the full history
  stays listed. Two reviewers deciding at once: the status-conditional update fails the
  second, and its review row rolls back with it. Only drafts are editable; `PUBLISHED` is final
  and records publication by hand; Facebook Page publishing (§ 16) runs separately and
  cancels its waiting posts when content is marked published by hand.

  (`workspaces.timezone`), DST-aware; calendar weeks start on Sunday.
- **Audit.** Every marketing mutation is audited in its transaction with field names and

## 12. Orchestration engine and the AI Marketing Manager

Code: `src/server/orchestration/`. Migration `20261010120000_orchestration_core` (tables
`automation_policies`, `agent_runs`, `agent_tasks`). Rules later capabilities must keep:

- **One engine for every workflow.** A workflow is a fixed graph of tasks
  (`WorkflowDefinition`); a run persists every task with its state, attempts, lease,
  `run_after` and output. `executeRun` advances a run step by step and can be called again
  from anywhere (request `after()`, the scheduler, the "continue" button) — a crashed or
  interrupted runner loses nothing. Readiness, failure propagation, run outcome, backoff
  and schedule slots are pure (`planner.ts`) and unit-tested.
- **Reliability.** Retries with exponential backoff (`TaskError(code, retryable)`;
  unexpected errors are retryable), per-task timeout via `AbortSignal`, leases recovered by
  `recoverStaleTasks`, cancellation (a late result is discarded because writes require the
  current lease token), idempotent runs (`(workspace_id, idempotency_key)` unique).
- **Authority.** A run acts for a member (`requested_by_user_id`; for scheduled runs the
  policy's delegate — the admin who enabled automation). Before every task the engine
  re-checks that member still holds `automation.manage`; otherwise the run stops with
  `actor_no_access`. Handlers receive that member's `TenantContext` and call the normal
  services (same permission checks, audit and AI limits as a person).
- **Risk classes and approvals.** Tasks are `INTERNAL`, `EXTERNAL` (publishing,
  messaging) or `SPEND`. Only `INTERNAL` tasks run without a person. An `EXTERNAL`/`SPEND`
  task must define `describe` (refused at `createRun` otherwise): deterministic code that
  states the exact action (and, for `SPEND`, an integer amount in minor units plus an ISO
  currency). The engine stores that snapshot and its SHA-256 over canonical JSON
  (`approval-snapshot.ts`) and sets the task `NEEDS_APPROVAL`; its dependents wait (they
  are not cancelled) and the run becomes `NEEDS_ATTENTION` once nothing else can move.
  `decideApproval` (`approvals.ts`, `automation.approve` — owners and admins, membership
  re-checked inside the transaction) records one immutable `agent_task_approvals` row per
  request round, only while the task still waits for exactly the hash the person was
  shown and the run is open. Approving grants **one** execution of that task: before the
  claim the engine re-describes the action and re-checks the approver; a different hash
  or a lost right voids the grant and asks again (`approval_stale`). The claim consumes
  the grant, so a retry or anything else needs a new approval. Rejecting fails the task
  (`approval_rejected`), which cancels its dependents and fails the run. Cancelling a run
  voids unused grants; late or duplicate decisions are refused. An `EXTERNAL`/`SPEND` task
  whose runner died is failed `outcome_unknown`, never replayed. Every request, decision
  (with its snapshot), stale grant and use is audited. Decisions are protected by triggers
  (no updates except the decider's account being deleted; grant must match the current
  approved round). No real publishing or ad-spend handler exists yet.
- **Emergency stop.** `automation_policies.paused` halts every run and the scheduler for
  the workspace immediately: it is checked before each task and again inside the claim
  transaction (workspace row lock shared with the stop), so it overrides approvals too;
  resuming continues where runs stopped. Policy changes, stop/resume, runs, failures,
  approvals and drafts are audited.
- **Scheduling.** One tick recovers stale tasks, starts due planning runs once per slot
  (compare-and-set on the policy version; missed slots are skipped, not replayed) and
  advances active runs. A scheduler calls `POST /api/internal/automation-tick` every 1–5
  minutes with `Authorization: Bearer $AUTOMATION_CRON_SECRET` (unset = 404; 12 calls per
  10 minutes; counts-only response), e.g.
  `*/2 * * * * curl -fsS --max-time 300 -X POST -H "Authorization: Bearer $AUTOMATION_CRON_SECRET" https://<app>/api/internal/automation-tick`;
  `pnpm automation:tick` does the same from a full source tree. Approved launches and
  sends start immediately after approval; the tick is what recovers them after a crash. Event-driven triggers are not implemented yet.
  The tick's 4-minute budget is checked before every item of every phase (a long phase
  stops early: `cutShortPhases`, status `partial`), and a video job renews its lease on
  every poll with writes fenced on the state it read, so a runner that lost its lease
  never charges or stores twice (`docs/runbooks/OPERATIONAL_RELIABILITY.md` § 1).
- **First workflow: content planning** — observe (brand, goals, campaigns, pillars, the
  next 7 days in the workspace time zone) → AI ideas through the AI engine → drafts only if
  the policy allows (at most `max_drafts_per_run`, status DRAFT, never scheduled or
  published) → report. UI: `/{locale}/w/{slug}/autopilot` (editors view, admins manage).

## 15. Credits (usage-based billing)

Code: `src/server/billing/`. Migration `20261012100000_credits`.

- **Accounts**: one `credit_accounts` row per workspace, created lazily under a lock on
  the workspace row. Two balances: `subscription` credits (granted each period by the
  plan, they expire at renewal) and `purchased` credits (kept). Subscription credits are
  spent first. Plans (`pricing.ts`, provisional `PRICE_VERSION`): trial
  (`CREDITS_TRIAL_MONTHLY`), starter, growth and pay-as-you-go.
- **Hold → capture/release**: `generate()` (`ai-service.ts`, the single AI pipeline)
  holds the task's price in the same transaction that creates the generation row
  (idempotency key `ai_generation:{id}`); a success captures it (with the provider's
  token cost when known), any failure releases it. A workspace without enough credits,
  or over its daily, period or per-feature cap, is refused before the provider is called
  (`credits_insufficient`, `credits_daily_cap`, …).
- **Ledger**: `credit_ledger_entries` is append-only (trigger) and ordered by a
  `sequence` column; every grant, hold, capture, release and admin adjustment writes one
  entry. Balances never go negative (CHECK constraints).
- **Settings and admin**: the billing page shows balances, usage and the ledger; owners
  and admins (`billing.manage`) set caps. Auto-recharge is refused while no payment
  provider is configured (`getPaymentProvider()` returns null: choosing one is an
  operator decision). Platform admins grant credits and change plans at
  `/admin/credits` (audited) and see the provider-cost report there. Each rendered grant
  form carries a request key (`credit_ledger_entries.request_key`, unique per workspace):
  a double submit or a retried request is applied once.
- **Abandoned holds**: a hold never settled (the outcome write failed or the process
  stopped after the provider call) is released by the scheduler tick after 15 minutes
  (`releaseStaleHolds`), and a generation still pending behind it is marked failed.
- **Provisional prices**: the costs and plans (`PRICE_VERSION` `2026-10-provisional`) are
  shown to users with a notice that they are provisional and may change before the
  commercial launch; they are not a final price list.

## 16. AI social manager

Code: `src/server/social/`. Migrations `20261012110000_social_manager` and
`20261012120000_social_publishing`.

- **Channels**: Facebook Pages and their linked Instagram accounts, read from the
  workspace's Meta connection (`/me/accounts`). Page tokens are fetched for each call and
  never stored; every Graph call carries `appsecret_proof`. Pages are listed with Graph's
  cursor pagination (100 per request, at most 20 requests). **Permissions**: the Meta
  connection must grant `pages_read_engagement`, `pages_manage_engagement`,
  `pages_manage_metadata`, `pages_messaging`, `pages_manage_posts`,
  `instagram_basic` and `instagram_manage_comments`. The ads login does not request them
  (it asks for ads scopes only), so with a Business login configuration
  (`META_CONFIG_ID`) they must be added to that configuration; without them every call
  fails as `permission_missing`. Instagram webhooks also need the app's `instagram`
  webhook object set up in the Meta dashboard.
- **Receiving**: `POST /api/integrations/meta/webhook` reads the body under a 1 MiB cap
  while it streams (`readBodyCapped`: 413 as soon as it passes the cap, also for chunked
  bodies without a length) and verifies the HMAC of the raw body (`META_APP_SECRET`)
  before parsing; comments (Page feed, Instagram) and Page messages
  become `social_interactions` (deduplicated by platform id; echoes, the Page's own
  comments and stale events are skipped). Drafting runs after the answer (`after()`);
  the scheduler sweep (`automation-tick`) catches anything missed. A drafting attempt
  holds the message for 5 minutes (`drafting_until`) and records its draft only while it
  still holds the claim, so the webhook and the sweep never draft the same message twice.
- **Agents**: an agent has business information, tone, FAQ, policies, goals, allowed
  categories and a mode. `SOCIAL_REPLY` classifies and drafts; in `REVIEW` mode every
  draft waits for a person (`social.reply`). `AUTO` mode sends only when all hold:
  confidence ≥ the agent's minimum, an allowed category, inside Meta's 24-hour window for
  messages, a delegate who still has `social.manage`, the workspace's emergency stop off,
  and under the agent's daily automatic-reply cap. Complaints and low confidence are
  escalated, never auto-sent. The decision itself is atomic (`decideAutomatically`): the
  daily cap is counted and used under a lock on the agent, and the platform message is
  claimed in `social_auto_reply_claims`, unique on the platform's ids (not per workspace).
  When two workspaces manage the same Page (each with its own copy of the comment), only
  the first claim answers automatically; the other workspace's draft waits for a person.
- **Sending**: claimed once (`NOT_SENT → SENDING`); a lost answer is `UNCERTAIN` and is
  looked up on the platform before anything is sent again; sends stuck in `SENDING` for
  10 minutes become `UNCERTAIN`. Sends made by the system (the sweep, automatic replies)
  wait while the emergency stop is on, and an automatic reply also waits until its
  delegate again has `social.manage`.
- **Learning**: every approval, edit and rejection becomes a lesson (an example or a
  rule). After enough feedback the sweep runs `SOCIAL_LEARNING`, which _proposes_ new
  guidance; a person applies or dismisses it (`guidanceVersion` increases). Nothing the
  agent learns changes its behaviour without that approval.
- **Publishing**: approved or scheduled content can be queued to a Facebook Page from the
  content page (`content.publish`). The sweep publishes due posts: text and link, or —
  when the content has an attached image — a photo post with the first image (JPEG or
  PNG, at most 4 MiB, checked when queuing; anything else is refused, never dropped). The
  image is read from the workspace's storage on the server, its key, type, size and file
  signature checked again, and uploaded to `/{page-id}/photos` as multipart bytes: no
  storage URL is given to Meta, so private buckets keep working. A photo post has no link
  field, so the link is appended to the caption (stored as the post's message, which the
  lost-answer lookup matches). A missing or unreadable image fails the post before any
  call (`image_missing`, `image_unavailable`, `image_invalid`). Verified only against a
  stand-in Graph API; Instagram publishing is not supported. The sweep re-checks the approval first, claims
  each post once (the approval is part of the claim), and treats a lost answer as
  `UNCERTAIN` (looked up among the Page's own `published_posts`: exactly one unaccounted post with its text settles it; several stay `UNCERTAIN` for a person); a post stuck in
  `PUBLISHING` for 10 minutes also becomes `UNCERTAIN`. Publishing is never instant:
  queuing approved content means the next scheduler tick (an approved item's planned date
  does not hold it back), scheduled content goes out at its time. Waiting posts follow
  their content in the same transaction (`social/queued-posts.ts`): a new schedule or a
  calendar move moves them, unscheduling, marking published by hand or moving back to a
  draft cancels them (`unscheduled`, `marked_published`, `content_not_approved`); posts in
  `PUBLISHING`/`UNCERTAIN` are never touched, and content with such a post cannot be
  deleted (`publication_in_flight`). The content page names why due posts wait
  (`social/publishing-readiness.ts`: sending switched off, Meta not set up, not connected
  or expired, emergency stop, scheduler not run within 15 minutes) and maps every stored
  error code to an actionable message.
- **Metrics**: counts and median response time from real rows only.

- **Tenant guard**: `TENANT_ROOT_RELATIONS` covers every workspace-owned relation of
  `Workspace` and `APPEND_ONLY_RELATIONS` every relation into an append-only model; a test
  reads `prisma/schema.prisma` and fails when a new relation is not registered.
- **Credit ledger**: append-only in the database for DELETE too (migration
  `20261013090000_credit_ledger_no_delete`). A future workspace purge must
  `SET LOCAL flexibx.purge_workspace = '<id>'` in its transaction to delete that
  workspace's ledger rows (and only those).
- **Production configuration**: `src/instrumentation.ts` validates every environment
  group at start-up (`src/server/startup-env.ts`); in production an invalid value stops the
  start with variable names only. `AI_PROVIDER=fake`, `MAIL_TRANSPORT=test-outbox` and
  `STORAGE_DRIVER=test-memory` are refused in production unless
  `FLEXIBX_TEST_PROVIDERS=allow` and `APP_URL` is local (end-to-end runs only). Missing
  `AUTOMATION_CRON_SECRET` or `ENCRYPTION_KEY` is logged as a warning.
- **Scheduler**: `runScheduledAutomationTick` is the single entry point of the endpoint
  and of `pnpm automation:tick`: orchestration, the social sweep, abandoned credit holds
  and stopped video jobs (only when `VIDEO_PROVIDER` is not disabled). Each phase and each
  item is isolated (`failedPhases` in the summary); a scheduled planning run is created
  before its slot is advanced, so a failure never loses a slot.
- **Queues**: due posts and unsent replies exclude paused workspaces and workspaces
  without a usable Meta grant, so they never hold the head of the queue. A reply decided
  but not sent for 2 hours (AUTO) or 24 hours (approved) goes back to a person
  (`stale_reply`); a post more than 24 hours past its time fails (`missed_window`).
- **`SOCIAL_SENDING_ENABLED`** (off by default): replies, messages and publishing from
  every path. Approving or retrying is refused (`social_sending_disabled`), AUTO agents
  only draft, the sweep sends and publishes nothing; the social page shows a notice.
- **Channel access**: events are recorded, drafted (charged) and answered only for
  workspaces with an ACTIVE, unexpired Meta grant. Disconnecting Meta, Meta
  deauthorization / data deletion, or a send that finds the Page gone disables the
  channels and releases their automatic-reply claims (`social.access_revoked`).
- **Message ownership** (`claimMessage`, table `social_auto_reply_claims`): whoever
  answers a message owns it across every workspace that manages the Page — an AUTO
  decision, a person's approval, or the send itself takes (or refreshes) the claim, unique
  on the platform's ids. Another workspace's attempt is refused (`social_reply_claimed`,
  a code only: nothing about the other workspace is read or returned) before any decision
  is recorded; an older approved reply the scheduler finds for a message owned elsewhere
  fails (`claimed_elsewhere`). Private conversations are claimed as a whole
  (`thread:<id>`); a conversation claim lapses 24 hours after its owner's last reply and is
  taken over only if none of the owner's replies there is pending, being sent or
  uncertain. A comment's claim is released when its send definitively fails (refused,
  stale, confirmed not sent); a conversation keeps its owner when one message fails.
- **Duplicates**: a reply replaced by a newer draft is never sent (`social_reply_superseded`).
  Checking an UNCERTAIN reply or post reads up to 10 pages; when it cannot read them all it
  answers "unknown" and the item stays UNCERTAIN (`social_cannot_verify`).
- **Plan changes** (admin): carry the account version shown with the form; a repeated or
  stale request is refused (`stale_status`) and changes nothing; the audit entry records
  the previous plan.

## 21. Marketing intelligence (Pass 5)

Recorded campaign results, summaries and rule-based recommendations that a person reviews
and acts on. Nothing here estimates, forecasts or claims a cause; nothing is fetched from
a real analytics provider yet.

- **Model** (migration `20261018090000_marketing_intelligence`):
  - `metric_imports`: one per batch, with provider, source, `external_id` (unique per
    workspace and provider), status (`SUCCEEDED`, `FAILED`, `VOIDED`), row counts, error
    code and the first row issues.
  - `metric_observations`: append-only, one per campaign or content item, channel,
    metric, period (at most 92 days) and value. Counts are whole numbers; money is in
    minor units, with an ISO currency required for money and refused otherwise.
    `source_ref` is the identity of an observation within its provider.
  - `marketing_recommendations`: the state a person gave a finding (`OPEN`, `REVIEWED`,
    `DISMISSED` with a reason, `SNOOZED` until a date, `ACTED` with the draft it
    created), plus `version`.
  - `marketing_goals.target_metric`: an optional count metric that a goal's target is
    measured in.
  - Enums: `PerformanceMetric` (impressions, reach, engagements, clicks, conversions,
    revenue, spend), `MetricSource` (`VERIFIED`, `MANUAL`, `SIMULATED`),
    `RecommendationKind` and `RecommendationStatus`.
  - Database rules:
    - CHECK constraints for everything above, the counts of an import, and each
      recommendation state;
    - `VERIFIED` is refused until a real provider integration exists;
    - same-workspace and workspace-immutable triggers;
    - observations can never be updated or deleted except by their content item's
      deletion;
    - an import's identity never changes, and its only allowed change is voiding.
  - All three models are in the tenant guard (observations append-only). The six
    triggers are in the restore check list.
- **Ingestion** (`src/server/intelligence/ingestion.ts`, validation in `metrics.ts`):
  - **Entry points.** A person's CSV (`period_start,period_end,metric,value,currency,content_id`,
    at most 500 rows and 200 KB) and the `MetricsProvider` interface. The interface is
    provider-neutral and returns rows with a batch id; the only implementation is the
    deterministic `test-fixture` provider (`SIMULATED`, refused in production).
  - **Validation.** Every row is checked: dates, period order and length, no future
    period, known metric, value format and limits, currency rules, and content in the
    same campaign.
  - **Workspace lock.** Each workspace's imports run one at a time on a transaction
    advisory lock.
  - **Repeats and duplicates.** A batch already imported (same provider and batch id)
    returns the first result and stores nothing. A row whose identity was already
    recorded by a non-voided import is a duplicate if the value is the same, and a
    `conflict` if it differs; it is never overwritten. Two rows with the same identity
    and different values in one batch are refused.
  - **Failures.** A batch with no valid row, a provider failure, a timeout (15 s) or a
    malformed answer is recorded as `FAILED` with its code. A corrected retry is still
    possible.
  - **Voiding.** Voiding an import removes its numbers everywhere and lets corrected
    numbers in.
  - **Audit and permissions.** Every import is audited: `metrics.imported`,
    `metrics.import_failed` and `metrics.import_voided`. Importing and voiding need
    `campaign.manage`.
- **Summaries** (`analysis.ts`, pure and deterministic):
  - Each observation identity counts once, and numbers are computed per evidence class.
    Simulated numbers are shown apart and never added to recorded ones.
  - A campaign total uses its campaign-level rows for a metric when there are any, and
    otherwise adds up its content-level rows, so nothing is counted twice.
  - Money is totalled per currency and is never converted.
  - Reach is added across periods, which can count a person more than once. The metric
    definition on the page says so.
  - The page also shows a daily series of one count metric, per-content engagement
    rates, import history, freshness (last success, last failure, latest period) and
    filters (campaign, channel, metric, dates).
- **Recommendations:**
  - Findings are computed on every read, from recorded (not simulated) observations of
    the whole campaign. Each one has evidence: period, sample size, sufficiency and the
    numbers behind it. The page shows its explanation, suggested action and limits.
  - Thresholds (`rulesSchema`, validated; `DEFAULT_RULES`, shown on the page):
    - content is compared only with at least 500 impressions over at least 2 periods,
      and only when at least 4 items qualify;
    - weak means below 0.5× the campaign's median engagement rate;
    - a strong format is a content type whose median is at least 1.5× the campaign's
      median, with at least 2 items of that type and 2 others;
    - stale means an active campaign whose latest period is more than 7 days old, or
      whose last import failed;
    - a goal is judged after 25% of the campaign window, and is below target under 0.8×
      its pro-rata value;
    - spend is flagged above 1× the budget, in the budget's currency only.
  - Without enough evidence, the result is "more data needed" rather than a judgment.
  - State is stored only when someone decides, keyed by a stable fingerprint:
    - review, dismiss (with a reason), snooze (1–90 days; it reopens when it runs out),
      or reopen;
    - every decision is conditional on `version`, and refused as `recommendation_changed`
      when stale or when the evidence no longer supports the finding;
    - deciding needs `campaign.manage`.
  - Acting on a finding (below target, weak content, strong format; also needs
    `content.create`):
    - creates one `DRAFT` content item in the campaign, through `createContentIn`, with
      the evidence in its notes;
    - marks the finding `ACTED`, after which it is settled;
    - the draft then goes through the normal review and approval workflow. Nothing is
      published or sent.
  - Audit: `recommendation.reviewed|dismissed|snoozed|acted`.
- **UI:**
  - `/{locale}/w/{slug}/insights`, in the navigation for anyone with `analytics.view`.
    It shows: a provenance notice, filters, freshness, recommendations with their
    actions and decision history, campaign summaries (recorded with their source badge,
    budget against recorded spend, goals, a separate simulated block), the trend (SVG
    and table), the content comparison, the import form and history (for managers), and
    the rules and metric definitions.
  - The campaign page links to it.
  - Arabic and English; CSV and provider ids are shown left-to-right.

## 22. Meta Insights integration (Pass 6)

The workspace's own Meta connection read for insights into the existing imports,
observations, Insights page and recommendations — not a parallel system. Read-only:
nothing is written to Meta, published, sent or spent.

- **Connection** (reuses § 18's advertising connection, one per workspace):
  - With `META_INSIGHTS_ENABLED=true`, the existing Facebook Login asks for
    `pages_show_list`, `pages_read_engagement` and `read_insights` (Pages), and
    `instagram_basic` and `instagram_manage_insights` (Instagram professional accounts).
    With `META_CONFIG_ID`, the login configuration's permissions apply instead. The
    permissions actually granted are checked per kind of source.
  - The OAuth state stays as it was: stored as a hash, single use, ten minutes, bound to
    the person, workspace and platform.
  - The user token stays encrypted (AES-256-GCM, bound to the workspace and platform;
    the key is `ENCRYPTION_KEY`, outside the database). Page tokens are fetched from
    `/me/accounts` for each run and never stored.
  - The connection still requires `ads_read` (the advertising adapter's requirement), so
    an insights-only grant is refused. Recorded as a gap.
- **Sources** (`insights_sources`, migration `20261019090000_meta_insights_sync`):
  - A source is one of the workspace's `social_channels` (a Page or an Instagram
    account discovered from its grant by the Social Manager's Page sync), turned on by a
    person with `social.manage`.
  - The database keeps a source in its channel's workspace and never lets it change
    account.
  - Disconnecting Meta, Meta's deauthorize callback and its data-deletion callback turn
    every source off with the reason. The numbers already read stay, as history.
  - A run that finds the Page gone from the grant turns that source off (`access_lost`).
    So does a run that finds the Instagram account no longer linked to its Page.
- **Client** (`meta-insights.ts`, pure, `fetch` injected):
  - The Graph version is `META_GRAPH_VERSION`, configured in one place, and the metric
    names live in one catalog.
  - GET requests only, one metric per request, each with `appsecret_proof`. Answers are
    validated with zod.
  - Meta's error codes are mapped to codes; Meta's message is never kept.
  - Up to three attempts with exponential backoff and equal jitter (500 ms base, 8 s
    cap) for rate limits (4, 17, 32, 613, 80000–80014, HTTP 429), Meta-side errors
    (1, 2, 5xx), network errors and timeouts (15 s per request). An expired token (190)
    or a missing permission (10, 200–299) is never retried. The pause before a retry ends
    when the run's deadline passes, so retries never take a run past its time limit.
  - A metric Meta rejects (100) is "unsupported", a value that is absent is "missing",
    and only a value of 0 is zero.
- **What is read, and what it is linked to** (`insights-sync.ts`):
  - **Account level, daily:** a Page's `page_media_view`, `page_total_media_view_unique`
    and `page_post_engagements` (one request over the window), and an Instagram
    account's `views`, `reach` and `total_interactions` (`metric_type=total_value`, one
    day per request).
    - These are stored without a campaign (`campaign_id` NULL, `insights_source_id` set).
      They are shown on the source's card and never counted in a campaign's results or
      used by its recommendations.
    - A day is Meta's reporting day: the day before `end_time`.
  - **Posts:** each Facebook Page post Flexibx published for content in a campaign
    (`social_posts.external_post_id`, a reliable link) gets its lifetime
    `post_media_view`, `post_total_media_view_unique` and `post_clicks`. Its interactions
    are reactions + comments + shares as the post reports them.
    - Linked to that content and campaign, so they count in the campaign's results and
      recommendations.
    - Covers up to 25 posts published within 60 days.
  - **Not linked:** Instagram media (Flexibx does not publish to Instagram) and ad spend
    (an ad plan is not tied to a campaign). Nothing is attributed by guess.
- **Runs** (`insights_sync_runs`):
  - Triggered by a person's "Sync now" (`campaign.manage`, at most once per five
    minutes per source) or by the scheduled tick's `insights` phase (due sources of
    workspaces with a usable grant, five per tick, daily). The tick's external trigger
    is still not configured (§ 18).
  - A run claims its source with a five-minute lease. The database also allows only one
    RUNNING run per source.
  - A run whose runner died is marked ABANDONED by the next run, which resumes from the
    stored coverage.
  - Each run is bounded:
    - 14 account days per run, starting 3 days before the coverage end, because Meta
      revises recent days;
    - 28 days on the first run, never older than 90 days, and only complete days;
    - 200 calls and 90 seconds.
  - Outcomes: SUCCEEDED (with the metrics Meta does not offer listed), PARTIAL (a post
    gone, or a limit hit — what was read is stored) or FAILED, always with a code.
  - Retries after a failure: 1 h, then 2 h, 4 h … up to 24 h. Token and permission
    problems wait for a person; an expired token marks the connection EXPIRED.
  - Audit: `insights.source_enabled|source_disabled|synced|sync_failed|access_revoked`,
    with counts and codes only.
- **Storage** (`storeProviderBatch`):
  - Same workspace lock and batch identity as every import: the batch id is
    `run:{runId}`, source VERIFIED, provider `meta`. The database refuses VERIFIED for
    any other provider, and any `meta` row without its source.
  - The same value again is a duplicate. A different value is a revision: a new row with
    a later `observed_at`; the import counts `rows_revised`.
  - Summaries count the latest revision of each identity once.
- **Analysis changes:**
  - **One source per item and metric.** For one content item and metric, Meta's numbers
    replace a person's; the two are never added together.
  - **Views or impressions, never mixed.** Content is compared by impressions or, when
    an item has none, by views, and only within the larger group.
  - **Days, not periods.** The rule "observed over at least 2 days"
    (`minDaysPerContent`) replaces "2 periods", because a lifetime number is one period
    spanning many days.
  - **New metric.** `VIEWS` is a metric of its own, never added to `IMPRESSIONS`.
  - **Trend.** The trend plots single-day numbers only. A total over a longer period (a
    weekly import, a post's lifetime views) is not a day's value; it stays in the
    summaries, and the page says so.
- **UI:**
  - A "Connected sources (Meta)" card on the Insights page shows:
    - the connection's state: not configured, not connected, needs reconnection, or
      ready, with the missing permissions per kind;
    - each channel's status: off (with the reason), needs reconnection, syncing, not
      synced yet, failed, partly read (a limit was hit after some reads, or a published
      post is gone from Meta — never shown as up to date), may be out of date (no success
      for 48 h), or up to date;
    - last success, last attempt and next sync; the days covered; the metrics Meta does
      not offer;
    - the account-level totals of the last 28 covered days, marked "Read from Meta" and
      "not a campaign's result";
    - the last five runs with their codes;
    - "Sync now" and the source switches, for those allowed.
  - Recorded numbers carry their source badges ("Read from Meta", "Entered by a
    person").
  - Arabic and English; permission names and ids are shown left to right.

## 23. Creator Studio (Pass 8)

The Creator Studio is a video repurposing pipeline: one source file becomes reviewed,
reframed short clips. Operations: [`runbooks/CREATOR_STUDIO.md`](runbooks/CREATOR_STUDIO.md).

- **Data (migration `20261020090000_creator_studio`):**
  - Tables:
    - `creator_projects`;
    - `creator_sources` (the declared and the detected type, size and duration; probe
      fields);
    - `creator_jobs` (kind, state, stage, lease, deadline, attempts, idempotency key) and
      `creator_job_steps` (one per stage, with the credit hold, provider and `simulated`);
    - `creator_transcripts` and `creator_transcript_segments` (originals and
      translations);
    - `creator_clips` (bounds, suggested bounds, reasons, score, framing, review status,
      version);
    - `creator_exports` (a snapshot of the clip's bounds and framing at request time,
      plus the stored file);
    - `creator_project_events` (append-only log).
  - Every table has workspace triggers (same workspace, immutable `workspace_id`) and the
    tenant guard. A same-project trigger links jobs, transcripts, clips and exports.
  - CHECK constraints cover storage-key prefixes, state consistency, lease and clip
    ranges.
  - A partial unique index allows one active job per source, kind and target language.
- **Flow:**
  - **Upload:** `startUpload` validates the declared type and size, reserves a
    server-generated key and returns a 15-minute signed PUT. `completeUpload` checks
    that the object exists and has the declared size, then queues **ANALYZE** (free).
  - **ANALYZE** compares the magic bytes with the declared type, runs ffprobe, enforces
    the duration limit and stores the media properties. A rejected file's object is
    deleted.
  - **TRANSCRIBE** (requested by a person after the estimate is shown) extracts 16 kHz
    mono audio, calls the `TranscriptionProvider`, validates the timed text (ordered,
    inside the duration, bounded) and then runs **SUGGEST**: `ruleBasedClipSuggester`,
    at most 5 non-overlapping 15–60 s windows, each with reasons and a score.
  - **TRANSLATE** calls the `TranslationProvider` segment by segment and keeps the
    timing.
  - **EXPORT** needs an approved clip. It takes a snapshot of the bounds, then cuts, crops
    and scales to 720×1280, 1280×720 or 720×720, optionally burns in SRT subtitles,
    checks the output with ffprobe (H.264 MP4, exact size, duration within 0.5 s),
    stores it and charges.
- **Jobs:**
  - **Claiming:** a worker claims a job with a compare-and-set (`leaseToken`, 2-minute
    lease, 30 s heartbeat). Every write after that runs in `lease.write`, which locks the
    job row and refuses the write unless the token matches and the state is RUNNING. A
    worker that loses its lease therefore cannot commit or charge.
  - **Steps resume:** succeeded steps are skipped on a retry or a takeover.
  - **Timeouts:** each step has its own timeout (via `AbortSignal.any`) and FFmpeg is
    killed with SIGKILL. Jobs also have a 60-minute deadline and 3 attempts with
    backoff.
  - **Retry:** a failed or cancelled job is resumed in place.
- **Credits:**
  - **Hold per step attempt.** Each paid step attempt takes a hold
    (`creator:<job>:<stage>:<attempt>`, priced as feature × started minutes).
  - **Capture with the result.** The hold is captured in the same fenced transaction
    that stores the step's result. A failure, a cancel or a lost lease releases it (or
    the stale-hold sweep does).
  - **Simulated work takes no hold.**
  - `HoldRequest.units` was added for per-minute pricing.
- **Providers (`providers/types.ts`):** `TranscriptionProvider`, `TranslationProvider`
  and `ClipSuggestionProvider`.
  - The only transcription and translation implementation is the declared simulator.
    It is test-only, refused in production, and its output is labelled in the text, in
    the `simulated` columns and in the UI.
  - No external service is called.
- **Media tools (`media/tools.ts`):**

## 24. Creator Studio production capabilities (Pass 9)

Operations: [`runbooks/CREATOR_STUDIO.md`](runbooks/CREATOR_STUDIO.md) §§ 4 and 7–10.

- **Data (migration `20261021090000_creator_studio_production`):**
  - `creator_sources` gains `upload_mode` (`single` | `multipart`), the multipart
    upload id, part size and count, and the declared SHA-256. `creator_source_parts`
    holds each part's declared size and SHA-256 (CHECKs: parts 5–256 MiB, only the last
    may be smaller).
  - `creator_storage_deletions`: the queue and record of objects to remove (reason,
    provider, key, open multipart upload, attempts, last error code, next attempt,
    completion). Identity columns are immutable and a completed row cannot be reopened.
  - `creator_projects.status` gains `DELETING` (with `deleted_at`). A BEFORE INSERT
    trigger on sources, jobs, transcripts, clips and exports refuses rows for a project
    that is being deleted (`FOR SHARE` on the project row, so it serialises with the
    delete).
  - `creator_job_steps` gains the cost columns (local processing time; provider audio
    seconds, tokens and estimated cost) and a `checkpoint` JSON for partial results.
- **Providers:** `TranscriptionProvider` / `TranslationProvider` now declare
  `processing` (external or not, and region), the audio piece length and the price per
  audio second. `providersFromEnv` (`runtime-env.ts`, pure) builds the simulator or the
  OpenAI adapters (`providers/openai.ts`) behind the configuration gate. Provider
  failures are typed (`rate_limited`, `timeout`, `unavailable`, `rejected`, `auth`,
  `outcome_unknown`); only the safe ones are retried, and `outcome_unknown` never is.
- **Resumable upload:** `StorageService.multipart` (create, sign part, list, complete,
  abort) implemented for S3 and in memory. The server keeps the session (source row
  bound to workspace, project, uploader and expiry), signs one part URL at a time after
  the browser declares the part's SHA-256, and completes from `ListParts`. The worker
  downloads to disk with a size cap (`downloadToFile`) and verifies every part's hash in
  one pass (`hashFile`).
- **Checkpoints:** TRANSCRIBE (per audio piece) and TRANSLATE (per batch) save partial
  results on the step through the fenced lease write, so retries and takeovers continue
  without paying the provider twice; the customer's hold is captured once, when the step
  succeeds.
- **Deletion and export:** `deleteProject` (`project-service.ts`) and the sweep
  `processStorageDeletions` (`deletions.ts`, run by the worker every minute).
  `exportProjectData` returns a versioned JSON document.
- **Monitoring:** the worker's heartbeat (`creator-worker`) and eleven creator checks in
  `ops-status` (counts and ages only).
